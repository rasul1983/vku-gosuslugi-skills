# Сформированные документы и результаты

Перед подписью дождаться подготовки пакета УКП, определить имена XML/PDF по фактическому манифесту/контракту услуги и скачать штатным действием. Расширение PDF/XML само по себе не отличает сформированный файл от загруженного пользователем вложения.

Оригинальные байты сохранять в artifacts/<run>/<case>/generated с package.zip, XML/PDF, манифестом, снимком ответов и validation.json. Разделить состояние UI и проверку документов. Достижение УКП не подтверждает подпись/отправку; успешная отправка не доказывает XSD/полноту PDF.

## Снимок данных

applicantAnswers.value бывает строкой JSON либо обычной строкой. Декодировать объекты/массивы/кавычки/boolean/null, но не преобразовывать числовые строки в Number: потеряются ведущие нули и точность длинного счёта.

При прямом переходе последнего загрузчика в УКП предыдущий ответ ещё может не содержать его файлов. Пассивно сохранять исходящий getNextStep, объединять applicantAnswers и currentValue текущей отправки с приоритетом currentValue. Это только оракул теста; VM по-прежнему использует поддерживаемый контракт applicantAnswers, не cachedAnswers.

Не считать самый последний HTTP-ответ автоматически полным снимком. Дождаться подготовки манифеста и сохранять подходящий снимок в момент формирования пакета. Ответ карты может не включать выбранный объект: использовать реально нажатую карточку как независимое ожидание и отметить источник. Не выдумывать отсутствующий DTO.

## Проверки

`validate_package.py --zip <package.zip> --output <каталог> --name <первое-имя> --name <второе-имя> [--xsd <schema.xsd>]` безопасно извлекает только указанные сформированные XML/PDF. Требует lxml для XSD и pypdf для PDF; зависимости разрешать через доступный runtime или отдельное окружение проекта. Недоступная зависимость — неполная проверка, не PASS.

Синтаксис/XSD недостаточны: написать проверки активной цели/роли/пола получателя, обязательных данных, адресов, банковского режима, числа и данных детей, выбора МФЦ, полного текста исправления и состава активных вложений. Примеры из другого модуля использовать только после сопоставления с контрактом текущего.

PDF извлечь в текст, проверить заголовки/нумерацию всех детей, отсутствие непроинтерполированных переменных и смысл данных. Отрендерить страницы при доступном Poppler/PDF-навыке и визуально проверить релевантные варианты; явно указать, какие страницы действительно просмотрены. Рендер не равен визуальному просмотру.

Исходные ошибочные отчёты сохранять. После исправления оракула перепроверять тот же пакет в отдельном revalidation с происхождением ожиданий и проверкой SHA-256 оригиналов; не переписывать историю как будто сбоя не было.

## Восстановление и указатель

Если пакет не скачали во время раннего прогона, сначала искать его байты в trace. Если нужен запрос к хранилищу, использовать только наблюдавшийся контракт и собственные orderId/manifest из трассировки. Не подставлять произвольные IDs, не создавать/подписывать/отправлять заявление повторно ради файлов. Браузер с общим профилем не запускать параллельно.

Создать GENERATED_DOCUMENTS.md с прямыми ссылками на XML/PDF и проверки: последний пакет каждого кейса и история попыток. Отказы до формирования заявления не имеют XML/PDF. Полноту проверять по числу положительных кейсов с документами, а не по числу всех тестов.

Подробная методика смысловой сверки, перепроверки и восстановления: [document-oracles.md](document-oracles.md).
