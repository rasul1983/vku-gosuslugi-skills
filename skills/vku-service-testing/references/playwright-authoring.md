# Создание и сопровождение автотестов Playwright

## 1. Исполняемый проект

Развивать существующий тестовый проект, если он уже работает. Не заменять адаптеры и профиль новым каркасом без причины. bootstrap.py предназначен для нового пустого каталога: он создаёт инвентарь, конфигурацию и шаблон, но не готовые бизнес-кейсы. Пустой cases.mjs должен считаться незавершённой работой, а не зелёным запуском.

Границы кода: кейсы описывают ожидания и действия; адаптер взаимодействует с реальными компонентами; наблюдатель сохраняет пассивные сетевые факты; проверка документов содержит независимый смысловой контракт; репортёр сохраняет результат. Не встраивать все эти обязанности в один условный цикл по JSON.

Фикстуры профиля/файлов и авторизованный browser profile остаются локальными и игнорируются Git. URL/пути/порог задаются конфигурацией текущего проекта, а не постоянной привязкой навыка. Команды передавать с абсолютным cd. Отчёт должен позволять повторить конкретный кейс командой --grep с точным ID.

## 2. Один браузер, который действительно тестируется

Playwright persistent context использует отдельный userDataDir. Пользовательский обычный Chrome и автоматизированный Chrome — разные сессии; установленное расширение не связывает их автоматически. При совместной диагностике проверять PID/профиль/URL и скриншот именно запущенного контекста. Один worker и один процесс на профиль, не запускать login и test одновременно.

Вход пользователь выполняет вручную. login требует открытого stdin/TTY: иначе Enter не дождётся и окно закроется. Сессия ЕСИА может протухнуть/перенаправиться после перезапуска стенда. Это precondition/environment, не отсутствие поля формы. Проверить фактический экран до каждого повторного старта.

Не путать установку браузера и движок: Safari WebDriver не Playwright. Использовать выбранный пользователем поддерживаемый Chrome/Chromium и фиксировать версии. Не переустанавливать npm из-за ошибки пути к package.json.

## 3. Надёжный адаптер компонента

Порядок локаторов: доступные role/label/name → проверенная привязка к ID компонента → конкретная структура виджета. Не хватать первый input на странице. Перед fill/click проверить единственность и видимость; при неоднозначности сохранить описание и уточнить адаптер. Скрытый native checkbox может иметь видимый label, адрес — textarea, rich text — contenteditable, выбранный Lookup — карточку без combobox.

После действия ждать наблюдаемое состояние: display.id, ожидаемый заголовок/карточка, завершение нормализации, принятие файла, готовность SDK. Большой фиксированный timeout сам по себе не исправляет неверный селектор. Не использовать force, evaluate-запись в Angular state, request interception или подмену DTO как способ прохождения формы.

Адрес: последовательно поиск/улица/дом/квартира с ожиданием нормализации после каждого существенного выбора. Два клика до normalize могут выбрать дом для прежнего результата. Карту ждать по готовности SDK/справочника; «Ничего не найдено» до загрузки внешнего скрипта не всегда окончательно. Штатная «Выбрать» может выполнить переход сама — не делать лишний click по несуществующему «Продолжить».

Конкретные наблюдения по компонентам — [browser-runtime.md](browser-runtime.md). Их применять только после проверки текущего DOM; атрибуты реализации могут меняться.

## 4. Пример формы шага

Ниже иллюстрация API Playwright, а не обещание структуры любого экрана:

```javascript
await test.step('Укажите сведения (s12)', async () => {
  await expect(page.getByRole('heading', { name: 'Укажите сведения', exact: true })).toBeVisible();
  await page.getByLabel('Номер документа', { exact: true }).fill(data.documentNumber);
  const next = page.getByRole('button', { name: expectedButton, exact: true });
  await expect(next).toHaveCount(1);
  await expect(next).toBeEnabled();
  await next.click();
  await expect(page.getByRole('heading', { name: nextHeading, exact: true })).toBeVisible();
});
```

Для нескольких одинаково названных кнопок ограничить локатор конкретным компонентом; не добавлять .first() без объяснения. При тестировании disabled сначала проверить блокировку до заполнения, затем активацию после. Ожидание маршрута должно различать неверный экран, отсутствие перехода и выход во вход ЕСИА.

## 5. Разделение причин сбоя

| Класс | Пример | Что делать |
|---|---|---|
| Дефект формы | неверный nextDisplay, обе условные кнопки, чужой документ | сохранить входы/экран/ответ и описать минимальную правку |
| Дефект адаптера | поиск только combobox при textarea | исправить локатор по DOM и повторить затронутый кейс |
| Дефект оракула | последний файл отсутствует в старом снимке | сверить outgoing currentValue, перепроверить оригинальные документы |
| Предусловие | в профиле нет требуемого объекта/возраста | заблокировать только зависимые кейсы |
| Окружение | таймаут карты, ЕСИА, недоступный сервер | сохранить причину; ограниченный повтор после восстановления |
| Несовпадение версии | локальный экспорт новее публикации | подтвердить публикацию и начать новое заявление |

При сбое сохранять URL, display, DOM/HTML, screenshot, trace, исходящие/входящие данные в частные артефакты и ошибки сети. Данные могут быть чувствительными, поэтому не коммитить их в публичный навык. Не удалять первоначальный FAIL после исправления: следующая попытка — новая запись.

## 6. Побочные действия и конец

Подписание/отправку включать только в разрешённой области. Уже данное разрешение из текущего контекста учитывать; не требовать повторно без новой причины. Не переносить разрешение на другой домен/продуктив. В каркасе по умолчанию выключено. Перед эффектом сверить фактический origin, а не только начальный URL.

При неопределённом результате отправки сначала узнать состояние заявления. Повторный click/новое заявление без проверки может создать дубль. При блокировке подписи тест доходит только до partial/signing-only. Для успешного E2E нужна наблюдаемая отправка и финал. Для отказа — именно ожидаемый тупик с причиной и кнопкой, а не timeout.

## 7. Журнал и метрики

После каждого кейса писать актуальный статус и историю попыток с run ID, временем, SHA настроек, profile preconditions, expected/observed end, наблюдаемыми экранами, документами и причинами. Поддерживать RESULTS.md, RUN_HISTORY.md, COVERAGE.md и GENERATED_DOCUMENTS.md. Не ждать конца многочасового набора, чтобы потерять весь прогресс при остановке.

Различать planned, running, passed, failed, blocked, partial, probe-passed, manual, not-covered по принятой схеме проекта. Пробное посещение экрана не full E2E. Итоговая таблица показывает последний результат и историю; более свежий FAIL не прятать прежним PASS. Показатели попарного набора/веток/экранов/полей/документов отдельно. Инженерное исправление теста проверять локально и затронутым реальным сценарием; не расширять прогон без причины.
