# От требований и замечаний к исполняемому покрытию

## 1. Источники ожиданий

URL и JSON достаточны для начала анализа, но не заменяют регламент. Найти рядом административный регламент с приложениями, действующий чек-лист проверки, принятые решения, XSD и VM. Для правовых условий опираться на пункт регламента, для UI — на применимую редакцию чек-листа, для структуры данных — на DTO и контракт платформы. Если источника нет, проверить техническую достижимость, но бизнес-соответствие отметить неизвестным. По имеющемуся навыку форм читать [работу с регламентом](../../vku-vm-templates/references/regulation-to-screens.md) и [чек-лист](../../vku-vm-templates/references/reviewer-checklist.md).

Ожидание нельзя автоматически скопировать из screenRules и назвать независимым тестом. Плохое правило тогда подтвердит само себя. Сначала определить ожидаемый результат условия по источнику, затем проверить маршрут, подпись кнопки и XML/PDF на эту истину. Генерация технического графа полезна для инвентаря и поиска пробелов, но не заменяет оракул.

## 2. Матрицы до скриптов

Построить связанные таблицы:

- требование/замечание → сценарии → наблюдения → документы;
- экраны (обычные, вложенные, скрытые) → тесты и статус фактического посещения;
- переходы и их существенные исходы → тесты;
- кнопка/режим → условие → следующий видимый шаг → тест;
- поле/фасета → позитив/негатив/граница → уровень проверки;
- XML/PDF-поле → источник активной ветки → тест.

Покрытие экранов не доказывает покрытие всех условий перехода. Статическая попарная матрица не доказывает выполнение всех запланированных сочетаний. Общий процент не должен скрывать непроверенные профильные пути, дату границы, подпись или документ. Явно перечислить знаменатель каждой метрики и допущения.

## 3. Как уменьшить число кейсов

Начать с самого длинного допустимого пути: роль с максимальным составом документов, несовпадающие адреса, условные приложения, выбор подразделения, несколько объектов, подпись и финал. Затем покрыть противоположные исходы и оставшиеся цели, роли и способы результата. Один насыщенный кейс повторяемого списка включает все доступные способы добавления объектов; остальные используют минимально достаточный набор.

Попарный набор дополнять сочетаниями большего порядка, влияющими на правила: цель+роль+основание полномочий, семейный статус+орган регистрации+добровольное приложение, адресное основание+регион+субъект, последняя загрузка+канал результата. Формально невозможные сочетания исключить с причиной, а не генерировать как реальные кейсы.

Разные типы представительства тестировать отдельно. Пол подающего и получателя сочетать так, чтобы обнаружить ошибочную персонализацию. Профильный документ и вручную введённый документ — разные пути; ручной аналог не покрывает экран подтверждения профиля.

## 4. Обязательные семейства проверок

| Семейство | Содержательные проверки |
|---|---|
| Роли и цели | самостоятельная подача, допустимые представители, каждая цель, запрет чужих полномочий/документов |
| Вопросы и решение | оба исхода, активный список документов, сроки/результат по цели, работа поп-апов и ссылок |
| Профиль | подтверждение/редактирование, отсутствующие необязательные сведения, выходные ограничения XSD |
| Адреса | совпадают/отличаются, регистрация/проживание по основанию, адрес получателя при представительстве, отказ по территории |
| Возраст/даты | каждая применимая роль/цель, точный день границы и соседние дни, реальный формат профиля/поля |
| Повторяемые данные | один/много, разные источники/документы, удаление/редактирование, граница выбора документа, все объекты в XML/PDF |
| Ввод | required, неверный формат, границы длины, допустимые спецсимволы, пустая необязательная строка |
| Вложения | каждый загрузчик, применимость, обязательность, формат, количество, размер, перевод и подпись как разные объекты |
| Возврат | отключить ранее включённую ветку, сменить режим поиска/ввода, сменить канал результата, проверить пакет без старых сведений |
| Подписание/финал | ожидаемый способ, созданные файлы, отправка, успешный финал по цели и каналу |

Точное множество зависит от регламента. Не добавлять невозможные юридические сценарии ради симметрии таблицы.

## 5. Таблица кейса и ожидаемые кнопки

```text
Сценарий C-01. Название и назначение
Предусловия: версия/роль/состояние профиля; данные и файлы — ссылки в частных fixtures
Требования: R-...; замечания: Q-...

| Название экрана (ID) | Что выбрать или сделать | Ожидаемая кнопка |
| ... | ... | ... |
```

Кнопки проверять на каждом шаге, включая «Верно», ответы квиза, «Продолжить», «Перейти к подписанию», встроенное «Выбрать», если они предусмотрены. Зависимость от следующего действия и исключение единственной ПЭП устанавливать по действующему чек-листу. На квизе ожидать набор ответов, а не одну основную кнопку. Для двух условных next-кнопок проверить ровно одну видимую и её состояние enabled/disabled. Скрипт не должен нажимать допустимый «любой из двух» вариант — это скрывает дефект подписи.

Невидимый вычислитель записывать как технический шаг с результатом/наблюдением, не как требующий клика экран. Заголовок в таблице раскрывать так, как пользователь реально увидит его для данной роли/пола; ID оставить для диагностики.

## 6. Невыполнимые предусловия

Не менять профиль/возраст и не снимать ограничения исходной формы ради удобства тестов. Если нужного профильного объекта нет, отметить путь blocked/not-covered; не подменять его ручным вводом. Если владелец предоставил тестовый порог, хранить его отдельно, указать отличие от штатного, запросить возврат только при наступлении оговорённого условия. Успех с тестовым порогом не подтверждает исходную возрастную границу.

Не создавать новый аккаунт без задания. Пользовательское ручное подтверждение тупика отмечать manual, включая фактически проверенную границу; не выдавать за автоматический успех. Остальные независимые сценарии продолжать.

## 7. После изменения версии

Зафиксировать SHA настроек и дату публикации на стенд. Если новый расчёт отсутствует в наблюдаемом маршруте, сначала сверить публикацию/черновик/новое заявление; не чинить скрипт под старую форму, чтобы он «прошёл». Результаты прошлой версии сохранить. Регрессия затрагивает изменённые узлы, их входящие/исходящие ветки, кнопки, поля документов и возвраты; полное повторение цикла определять по масштабу и заданию.
