# Независимая проверка документов и истории

## 1. Пакет сохраняется на каждую положительную попытку

Скачивать сформированные платформой XML/PDF в точке генерации перед подписанием. Имена определить по текущим настройкам MiniApp/манифесту; пользовательское приложенное PDF не является PDF заявления. Сохранять ZIP, исходные XML/PDF, SHA-256, манифест и источник ожиданий в отдельном run/case/attempt. Не перезаписывать байты и отчёты прошлой попытки.

Отрицательный кейс, завершившийся до генерации, не обязан иметь документы. Знаменатель полноты пакетов — положительные попытки/кейсы, достигшие генерации. Достижение УКП, получение файлов, подписание и финал — разные статусы.

## 2. Снимок для сравнения

Наблюдать последний outgoing getNextStep: currentValue финального загрузчика может ещё отсутствовать в прежнем applicantAnswers. Объединять их с приоритетом currentValue только в оракуле теста. Для VM сохранять поддерживаемый контракт applicantAnswers, не советовать брать кеш.

Декодировать JSON-объекты/массивы, но длинные числовые строки/ведущие нули не превращать в Number. Зафиксировать выбранную карточку карты как самостоятельный UI-факт, если ответ не содержит её полную структуру. Записывать происхождение ожидания каждого поля, а не заполнять неизвестное предполагаемым значением.

## 3. Три слоя проверок

| Слой | Проверки | Чего он не доказывает |
|---|---|---|
| Структура | XML well-formed, реальная XSD с импортами; PDF читается/имеет страницы | правильность роли, данных и полноты |
| Смысл | активные значения и отсутствие лишних, состав всех объектов и файлов | отсутствие визуальных дефектов |
| Визуальный | просмотр реально отрендеренных страниц PDF | полноту непроверенных веток/пределов |

Проверять не только «значение где-то встречается»: использовать namespace-aware XPath, число элементов, правильный субъект/блок, атрибуты и отсутствие альтернативы. Для PDF извлечение текста может менять пробелы и порядок, поэтому нормализовать только представление, сохраняя смысл и полноту. Отсутствие строки в тексте PDF иногда требует визуальной проверки, а не мгновенного вывода о пропаже.

## 4. Контракт смысловых утверждений

- Правильная цель, получатель и подающий; пол/склонение/основание представительства; человекочитаемые значения вместо внутренних кодов.
- ФИО, даты, контакты, идентификаторы, документы и адреса каждого субъекта. При совпадении адресов ожидается активный исходный адрес.
- Банк из активного режима; старый альтернативный источник отсутствует. Счета сравнивать строками без потери цифр.
- Все повторяемые объекты в верном количестве и порядке; каждый способ документа; соответствие акта/свидетельства; нумерация PDF.
- Применимые дополнительные документы, перевод и подпись, каждый файл; никакие приложения чужой цели/отключённой ветки не попали в пакет.
- Конкретное подразделение/канал результата и соответствующие формулировки.
- Полный длинный текст: после разрешённого разбиения собрать части и сравнить с исходным, включая символы вне BMP. Не проверять только наличие первого фрагмента.
- Пустые необязательные элементы отсутствуют; 0/false не потеряны; нет неразрешённых переменных/директив.
- Календарные даты не сдвинуты; XML-текст после разбора равен источнику со спецсимволами.

## 5. Помощник и границы

Вызов исполняемого помощника (имена заменяются фактическими):

```bash
python3 <skill>/scripts/validate_package.py --zip <package.zip> --output <new-check-dir> --name request.xml --name request.pdf --xsd <schema.xsd>
```

Для рендера --render и при необходимости --pdftoppm <binary>. --name повторяется для каждого имени; флага --names нет. Локальный max-bytes помощника — ресурсный бюджет анализа, не лимит вложений услуги. Помощник не выполняет весь смысловой контракт и не просматривает изображения вместо агента; соответствующие проверки дописать и явно отметить результаты.

## 6. Если ранний пакет не сохранён

Сначала искать сохранённые байты в trace/приложениях отчёта. Если требуется хранилище, использовать только наблюдавшийся контракт и манифест данного заявления в разрешённой сессии. Не угадывать IDs, не подписывать и не подавать заново ради восстановления файлов. Если байтов нет, отметить отсутствие доказательства; нельзя назвать пакет проверенным по скриншоту ссылки.

## 7. Перепроверка после ошибки теста

Если найден дефект оракула, сохранить исходные FAIL-отчёты. В revalidation записать причину, исправленный источник ожиданий, SHA до/после и результаты на тех же байтах. Не называть новый запуск тем же исходным прогоном. Индекс документов может показывать «исходный FAIL; перепроверка PASS», с прямыми ссылками на оба отчёта. Без совпадения хешей это новые документы, а не перепроверка старых.

Создать индекс по кейсам: последняя попытка/версия → XML → PDF → проверки → страницы визуального просмотра, ниже история. Наличие N ZIP не равно N покрытым кейсам: учесть повторы, исторические версии, отсутствующие документы и ожидаемые отказы. Итог передачи отдельно сообщает, сколько пакетов проверены по XSD/смыслу/визуально и что осталось неподтверждённым.
