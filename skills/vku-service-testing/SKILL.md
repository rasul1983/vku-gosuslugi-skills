# Тестирование услуг ВКУ

## Вход и результат

Обязательные входы: URL тестируемой формы и абсолютный путь к JSON её настроек. Принимать их из сообщения, без требования переименовать файл или изменить его содержимое. Остальные материалы искать рядом: XSD с импортами, VM, регламент, существующие тесты и подтверждённые решения владельца. Отсутствие XSD не блокирует UI-прогон; проверку XSD тогда явно оставить неподтверждённой.

Результат: исполняемые скрипты Playwright, таблицы кейсов, актуальные статусы, история попыток, фактическое покрытие и оригинальные сформированные документы с отчётами проверок. Писать скрипты по модели и наблюдаемому DOM; запись codegen нужна только если пользователь её выбрал. Пустой cases.mjs или один план без реализации не считать завершённой работой.

## Подготовка

1. Настройки услуги использовать только для чтения. Зафиксировать путь и SHA-256; не создавать «исправленную» копию. При смене экспорта пересмотреть ожидания и отметить новую версию результатов.
2. Проверить существующий проект тестов. Если он есть, развивать его, сохранив профиль, результаты и рабочие адаптеры. Для нового проекта использовать [bootstrap.py](scripts/bootstrap.py):

```bash
python3 <путь-навыка>/scripts/bootstrap.py --url '<URL>' --settings '<JSON>' --output '<новый-каталог>'
```

Скрипт создаёт инвентарь и каркас, но не придумывает бизнес-ожидания. Автор навыка обязан заполнить cases.mjs и необходимые адаптеры до передачи пользователю. В assets/project нет данных конкретной услуги.
3. Прочитать [проектирование кейсов](references/case-design.md). Разобрать основной и циклический графы, внешние экраны, logicComponents, кнопки и источники значений. Смысл ожидаемого маршрута проверять независимо от screenRules, чтобы тест не воспроизводил ошибку самой настройки.
4. Прочитать [браузерный процесс](references/browser-runtime.md) перед реализацией адаптеров/запуском. Профиль браузера отдельный, один worker на профиль; не путать его с обычным Chrome пользователя. Вход пользователь выполняет вручную. Команды давать с рабочим каталогом.

## Кейсы и запуск

Начинать с длинных веток: роли/пол получателя, цели, семья, документы, адреса, способы результата и подписи. Выбирать достижимые комбинации, использовать попарное покрытие для сокращения повторов, затем добавлять важные сочетания большего порядка, возрастные/календарные границы, возвраты, пустые необязательные поля и неправильный ввод. Полный перебор и попарное покрытие называть разными результатами.

Оформлять кейсы таблицами: «Название экрана (ID) | Что выбрать или сделать | Ожидаемая кнопка». Персонализацию раскрывать в ожидаемый текст по получателю услуги. Способы добавления детей объединять в один расширенный кейс, остальные ветки проводить с коротким набором.

Для каждого сценария проверить логический конец: отправка и успешный финал либо ожидаемый отказ. Достижение УКП отдельно отмечать как частичное прохождение. У подписания/отправки должна быть авторизация из текущего задания или сохраняющегося контекста. Уже данное разрешение для конкретного стенда учитывать без повторного запроса; не переносить его на другую услугу/домен. В конфигурации каркаса эффекты по умолчанию выключены; включать их только в разрешённой области.

Запускать и исправлять адаптеры по артефактам, без подмены Angular state, ответов или сетевых запросов формы. Различать дефект услуги, ошибку скрипта, неподходящий профиль и сбой окружения. После сбоя определить причину, не размножать одинаковые попытки; завершать независимые проверки. Для внешнего таймаута допустим отдельный повтор после проверки окружения/восстановления входа. При непонятном результате отправки сначала проверить состояние заявления; не отправлять его заново вслепую.

Отмечать статус после каждого кейса и сохранять историю ошибок/прерываний. Более поздний сбой не скрывать прежним успехом. Ручную проверку подписывать как ручную и не расширять её на непроверенную точную границу.

## Документы и доказательства

Если услуга формирует XML/PDF, прочитать [проверку артефактов](references/artifacts.md). Скачивать именно документы VM до подписания, сохранять исходные байты отдельно по каждой попытке. Загруженные пользователем вложения не выдавать за сформированные документы. Проверять XML/XSD, смысл активных веток, PDF-текст и рендер; визуально просмотренные страницы отмечать отдельно.

Детерминированный помощник [validate_package.py](scripts/validate_package.py) извлекает выбранные имена из ZIP и проверяет синтаксис/XSD/PDF; бизнес-сверку агент дописывает по контракту услуги. Если зависимости или XSD отсутствуют, не подменять проверку заявлением об успехе.

Покрытие экранов вычислять по наблюдениям успешных реальных прогонов, включая finishedAndCurrentScreens/скрытые вычислители и вложенные экраны. Запланированные шаги, запись пользователя и ручной ввод вместо профильного компонента не являются доказательством автоматического покрытия.

## Передача

Сохранить понятные RESULTS.md, RUN_HISTORY.md, COVERAGE.md, каталог документов и команды повторного запуска. В итоговом сообщении: сколько пройдено, какие ошибки исправлены в скриптах/обнаружены в форме, что заблокировано и где артефакты. Условия завершения вроде возврата временного тестового порога записывать в проект и напоминать при фактическом выполнении условия. Не сохранять пороги, идентификаторы или разрешения отдельной услуги как общие настройки других услуг.

При анализе формы/VM дополнительно использовать доступный vku-vm-templates, но новый навык тестирования остаётся работоспособен с собственными ссылками и каркасом.
