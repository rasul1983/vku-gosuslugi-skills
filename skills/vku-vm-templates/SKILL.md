# Формы и документы ВКУ

## Входы и границы

Для формы нужны настройки, описание задачи и доступные нормативные/бизнес-требования. Для VM дополнительно нужны XSD с импортами, фактические DTO разных веток и эталоны того же платформенного движка. Искать материалы в рабочем проекте; отсутствие источника отметить, но выполнять независимую часть работы.

Полный JSON настроек читать без изменения. Пользователь переносит рекомендации в конструктор. Не создавать исправленную копию настроек. VM создавать/изменять только в рамках запроса. Данные другой услуги не становятся требованиями текущей.

## Обязательный выбор подробного раздела

Не ограничиваться общим чек-листом ниже. Перед изменением соответствующей части прочитать профильный раздел полностью:

| Задача | Раздел и результат |
|---|---|
| Новая форма, анализ НПА, восстановление требований | [Регламент → экраны](references/regulation-to-screens.md): реестр пунктов и приложений, роли/цели, документы, модель до ID, трассировка к тестам |
| Замечания, повторная проверка версии, UI-тексты | [Чек-лист проверяющего](references/reviewer-checklist.md): история итераций, статусы доказательства, требования по типам экранов, спорные критерии |
| Маршруты, возвраты, две подписи кнопки | [Переходы и кнопки](references/routing-and-buttons.md): достижимые состояния, карточки И/ИЛИ, nextVisible, полный пример настройки |
| JSON Logic, linkedValues, возраст, персонализация | [Вычисления](references/jsonlogic-linkedvalues.md): пространства путей, v1/v2, оболочки полей, полный календарный пример |
| Создание/исправление XML/PDF VM | [Контракт данных VM](references/vm-data-contract.md) и [диалект Velocity](references/velocity-rules.md): активные ветки, пустые поля, файлы, даты, PDF, диагностика |
| Длина, допустимые символы и обязательность | [Форма ↔ XSD](references/xsd-field-contracts.md): точный XPath, все фасеты, профильные поля, воспроизводимые контрпримеры |
| Справочник, карта, замена шаблоном | [Справочники и шаблоны](references/reference-books.md): структура значения, публикация, индексация и зависимости |
| Реальные автотесты, документы и журнал | [vku-service-testing](../vku-service-testing/SKILL.md) |

Сначала регламент и приложения, затем модель. Проверка реализации по JSON не заменяет проверку права/комплекта данных по нормативному источнику. Различать требование услуги, критерий проверки, технический контракт, наблюдение платформы и принятое исключение. Не переносить условие одной услуги в другую.

## Проектирование и проверка формы

Прочитать [процесс работы с формой](references/form-workflow.md) и [проверенные особенности платформы](references/verified-platform-behavior.md).

Построить инвентарь экранов, компонентов, основного и циклического графов, внешних шагов, logicComponents, вычислений и кнопок. Начало определять по init/initScreens/признаку первого экрана. Числа в ID не задают порядок.

По целям и ролям составить модель сценариев до назначения новых ID. Для существующей формы соблюдать выбранный пользователем порядок; изменение подписи кнопки не требует перестановки экранов. Ввод данных и последующая загрузка документов — разные действия. Вопросы, зависящие от только что введённых данных, должны оставаться после этих данных.

Для новых локальных ID использовать согласованный формат sN и sN_cN; существующие системные идентификаторы не переименовывать. Проверить точные ссылки, похожие кириллические/латинские буквы и зависимости перенесённых шаблонов.

Переходы анализировать по достижимым состояниям, включая возвраты. Допустим один признак, если он однозначен. Предлагать минимальное исправление воспроизведённого пробела/пересечения. В карточках с объединением условий только через И альтернативу ИЛИ задавать отдельными карточками перехода.

Различать пути DTO, source linkedValues и диалект JSON Logic. Не подменять работающий диалект стандартной библиотекой JSON Logic без проверки. linkedValues экспортируется массивом; ожидания типов и точек отсчёта проверять фактическими ответами.

Сложную видимость двух взаимоисключающих кнопок можно вычислить ValueCalculator до целевого экрана. ref.relatedRel — ID вычислителя, path — arguments.<имя>. type/action продолжают выполнять штатный следующий шаг, маршруты остаются в screenRules. Проверять кнопку по следующему видимому действию, включая выбор подразделения.

## XSD и Velocity

Прочитать [сверку XSD](references/xsd-review.md) и [правила Velocity](references/velocity-rules.md).

Сопоставить каждый вход с условием активности, JSON-путём, XML XPath и PDF-представлением. Для неоднозначной структуры получить фактический DTO. Источник VM — applicantAnswers/подтверждённые псевдонимы; cachedAnswers не использовать. Системные сформированные файлы описывать отдельно.

XSD задаёт структуру и допустимость XML; бизнес-источник — смысл и состав; DTO — фактические данные; эталоны того же движка — синтаксис. Не исправлять XSD молча и не пропускать обязательный элемент для обхода ограничения.

Использовать подтверждённый платформой синтаксис. Успех стандартного Apache Velocity не доказывает поддержку конструктором. До проверки текущего движка обходиться прямыми условиями/циклами внутри корня, без пользовательских макросов и вычислительного пролога.

XML: точный namespace, порядок, choice, кратность, необязательные строки без пустых элементов. PDF: формат действующего эталона, применимые разделы, последовательные номера повторяемых блоков, правильные данные получателя/представителя, выбранный способ результата. Значения справочника и коды не путать.

Проверять реально сформированные XML/XSD и PDF-текст/рендер, включая спецсимволы и границы. Для независимого браузерного исполнения использовать [vku-service-testing](../vku-service-testing/SKILL.md). Статические проверки отделять от штатного рендера и успешной отправки.

## Выход

Дать только актуальные действия в конструкторе: причина, точный экран/компонент, настройка или выражение, ожидаемый результат. Сохранить матрицу сценариев и открытые вопросы. Уже выполненные изменения и принятые исключения не предъявлять повторно. Для VM передать шаблоны, mapping, проверки и непокрытые случаи. Указывать происхождение требований и предел доказательства.
