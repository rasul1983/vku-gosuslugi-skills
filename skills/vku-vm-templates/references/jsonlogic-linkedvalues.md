# JSON Logic, linkedValues и календарные проверки

## 1. Сначала контракт, затем выражение

Для каждого аргумента записать: ID компонента-владельца, argument, входные пути, фактические типы/форматы, ожидаемый тип, пустое значение, условия посещения, потребителей и момент пересчёта. Не копировать ID из эталона; ссылки на отсутствующий экран делают перенесённый шаблон неработающим.

Три пространства путей не взаимозаменяемы:

| Контекст | Пример синтетического пути |
|---|---|
| Исходящий/входящий DTO | scenarioDto.applicantAnswers.s12_c1.value |
| JSON Logic данного диалекта | answer.s12_c1.value |
| linkedValues.source развёрнутого ответа | s12_c1.title |
| Зависимость от вычислителя | ID компонента + arguments.result |
| Подстановка в HTML | ${result} после настройки аргумента |

DTO value может быть строкой JSON; после платформенного декодирования объект уже не имеет дополнительного value. Lookup может содержать id/text/originalItem, а не value. Путь подтверждать конкретным ответом. Не менять пути в работающем диалекте автоматически на стандартный `{ "var": ... }`. Строка с путём здесь может интерпретироваться иначе, чем обычной библиотекой JSON Logic.

## 2. Где вставлять код

Поле «Вычисляемые аргументы (linkedValues)» — массив объектов. Поле «Код JSON Logic» внутри отдельного аргумента — только объект jsonLogic. Не вставлять внешнюю оболочку туда, где конструктор её уже создал. При сообщении FieldComponent["linkedValues"] проверить тип массива прежде сложной логики.

Пример аргумента с явным boolean на всех выходах:

```json
[
  {
    "version": 1,
    "argument": "hasDocument",
    "jsonLogic": {
      "if": [
        {"notEmpty": ["answer.s12_c1.value"]},
        true,
        false
      ]
    }
  }
]
```

notEmpty — платформенный оператор, его поддержку/семантику проверять на действующем движке. Не путать пустую строку с boolean false и числом 0. Для необязательного источника определить, должно ли отсутствие означать false, пропуск проверки или ошибку.

## 3. Версия 2 и выражения

Не смешивать `jsonLogic` и `definition` произвольно. Для версии 2 сначала открыть предоставленную документацию и рабочий пример текущего конструктора: доступность asDate, имена expression1/expression2, кавычки аргументов и порядок зависимостей — контракт конкретной версии.

Структура подтверждённого паттерна сравнения календарных дат (синтетические ID):

```json
[
  {
    "version": 2,
    "argument": "inPeriod",
    "definition": {
      "expression1": "asDate(arg3) >= asDate(arg1) && asDate(arg3) <= asDate(arg2) ? true : false",
      "arg1": "'${s10_c2.arguments.startDate}'",
      "arg2": "'${s10_c2.arguments.endDate}'",
      "arg3": "'${s11_c1.arguments.date}'"
    }
  }
]
```

Не обещать работоспособность до проверки, что эти три аргумента существуют и уже вычислены. Строковые литералы в definition могут требовать внутренних одинарных кавычек. Сложение года и суффикса даты — конкатенация строк после проверки типа, не арифметическое прибавление года. Успех версии 1 не доказывает правильность той же оболочки в версии 2.

## 4. Подстановки и условный текст

Для INFO проверить interpolationEnabled и каждую ${...}. Значение карты/сложного объекта сначала вынести в собственный linkedValue с source, затем подставлять ${officeTitle}/${officeAddress}. Прямое ${answer...} в HTML не является заменой настройки источника. Для условного текста source/expressions брать из подтверждённого экспорта; не выдумывать синтаксис expressions.

Для персонализации: профиль подающего при самостоятельной подаче, данные/роль получателя при представительстве. Техническое значение варианта может отличаться от печатного текста. Нельзя печатать машинный код ответа вместо «Вдовец/Вдова» либо человекочитаемого основания представительства.

## 5. Календарный возраст

Уточнить субъект, дату отсчёта, нижнюю/верхнюю границу и строгость: «младше N», «не старше N», «до N включительно» не равнозначны. Возраст в полных годах:

```text
age = year(today) - year(birth)
      - (monthDay(today) < monthDay(birth) ? 1 : 0)
```

Не делить миллисекунды на 365 дней. Не вычитать годы из строк dd.MM.yyyy по ISO-позициям. Профиль может давать dd.MM.yyyy, ручной DateInput — ISO; сначала подтвердить формат. Для today в ISO можно выделить yyyy-MM-dd; не трактовать UTC-время как локальный день без проверки. Для 29 февраля и даты на границе суток зафиксировать требуемое поведение по правилам услуги/платформы.

Для ISO JSON Logic можно выразить age через substr года (0,4), месяца (5,2), дня (8,2), арифметическое вычитание и if/or/and. Сравнение месяца/дня должно учитывать ведущие нули и типы; числовое приведение движка проверять примерами. Не представлять неисполненную формулу как проверенную платформой.

Калькулятор, совмещающий применимость и проверку:

```text
если цель не требует ограничения: true
иначе если дата и today валидны: age соответствует пределам
иначе: false или отдельная ошибка согласно контракту
```

Переход true → продолжение, false → нужный тупик; при строгом boolean выходе не возвращать строку "false" без осознанного соглашения. На изученной платформе String-сравнения с true/false работали для boolean; не объявлять это ошибкой по одной статике и не распространять на все движки.

## 6. Поле даты и дополнительная защита

`birth <= today-18y` вместе с `birth >= today-Ny` задаёт включительный интервал дат, в который попадают и промежуточные возраста. Нижняя граница birth >= today-Ny включает точное N-летие; условие age < N его исключает. Совпадение этих механизмов нужно проверять, не выводить из названий ограничений.

Не снимать ограничения DateInput автоматически ради проверки тупика: если владелец сохраняет их, тупик — дополнительная защита. Отрицательный тест может оказаться недостижим из обычного UI; отметить это и выбрать допустимый граничный день для проверки калькулятора. Не подменять состояние/запрос ради прохождения теста.

Таблица минимум: за день до нижней границы, точная нижняя граница, обычный допустимый возраст, день до верхнего дня рождения, точное верхнее день рождения, день после, нет даты, неправильный формат, цель без проверки. Тестовый порог хранить как исключение среды с напоминанием о возврате штатного; не превращать его в требование услуги.

## 7. Отладка

Сохранить фактические входы, выполненный вычислитель и результат из arguments; проверить logicComponents/порядок исполнения и обновление после возврата. Если кнопки не переключились, сначала ID/path/тип результата/факт запуска, затем формула. Локальный симулятор диалекта должен воспроизводить именно подтверждённые операции; не проверять только тем же вычислителем, который породил ошибку. Истина ожидаемого результата — независимая таблица по требованиям.

## 8. Полный пример календарного вычисления

Синтетическая задача: проверка нужна только при s13_c1="Да"; дата рождения s12_c1 в ISO yyyy-MM-dd; верхний порог для демонстрации — строго младше 21. Число 21 не является требованием портала. Вне проверяемой ветки вернуть true; при отсутствии данных в проверяемой ветке — false. Функции, типы и форматы подтвердить на текущей платформе.

```json
[
  {
    "version": 1,
    "argument": "ageAllowed",
    "jsonLogic": {
      "if": [
        {"==": ["answer.s13_c1.value", "Да"]},
        {
          "if": [
            {"and": [{"notEmpty": ["answer.s12_c1.value"]}, {"notEmpty": ["variable.today"]}]},
            {
              "<": [
                {
                  "-": [
                    {"-": [{"substr": ["variable.today", 0, 4]}, {"substr": ["answer.s12_c1.value", 0, 4]}]},
                    {
                      "if": [
                        {
                          "or": [
                            {"<": [{"substr": ["variable.today", 5, 2]}, {"substr": ["answer.s12_c1.value", 5, 2]}]},
                            {"and": [
                              {"==": [{"substr": ["variable.today", 5, 2]}, {"substr": ["answer.s12_c1.value", 5, 2]}]},
                              {"<": [{"substr": ["variable.today", 8, 2]}, {"substr": ["answer.s12_c1.value", 8, 2]}]}
                            ]}
                          ]
                        },
                        1,
                        0
                      ]
                    }
                  ]
                },
                21
              ]
            },
            false
          ]
        },
        true
      ]
    }
  }
]
```

Формула вычисляет `год(today)-год(birth)-(день рождения ещё не наступил ? 1 : 0)`. Для dd.MM.yyyy позиции рождения другие: год 6..9, месяц 3..4, день 0..1; не менять позиции today, если он остаётся ISO. Формула не проверяет сама корректность/будущность даты и нижний возраст: их добавить по требованиям либо сохранить в поле. Для 29 февраля правило дня достижения возраста уточнить по применимым требованиям, не выбрать произвольно календарную политику библиотеки.

Маршрутизация: компонент вычислителя/arguments.ageAllowed = true → следующая форма; false → нужный возрастной тупик. Тип сравнения выбирать по подтверждённому экспорту. В наблюдавшейся реализации boolean работал с String и строками true/false; это не повод менять работающие правила или гарантировать такое приведение в любом движке.
