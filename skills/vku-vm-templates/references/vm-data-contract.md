# Данные, ветки и документы VM

## 1. Карта источников

До правки составить `поле по смыслу | условие активности | компонент/DTO | декодированная структура | XML XPath | PDF | обязательность | тест`. Сверить обе VM и все роли. Один пример JSON не доказывает структуру другой ветки.

Корень может быть scenarioDto либо готовые псевдонимы компонентов, которые обработчик разворачивает из applicantAnswers. Использовать подтверждённый контракт среды. Не обращаться к cachedAnswers и не добавлять дополнительное ['value'] к уже декодированному объекту. Для Lookup проверить id, text, title, originalItem.attributeValues отдельно: отображаемое имя не равно коду справочника.

Строки идентификаторов/счетов/серий не преобразовывать в числа. Пол, семейное положение и печатные формулировки определять по получателю услуги; подающий представитель — отдельная сущность. Машинный код варианта не должен попадать в заявление как человекочитаемое описание.

## 2. Активная ветка важнее непустого значения

Для каждой альтернативы сначала проверить управляющий ответ, затем поля этой ветки. Типовой пример — банк из справочника против ручного банка. После возврата оба источника могут оставаться непустыми; выбор «первый непустой» неверен. Тот же принцип для адресов, семейных документов, целей, полномочий и профильного/ручного ввода.

Если адреса совпадают, источник второго адреса — подтверждённый первый адрес. Если документ/подтверждение не требуется по текущей цели, старое вложение не должно попадать в пакет только из-за наличия в DTO. Это не заменяет проверку очистки UI, но защищает документы от прежних ответов.

## 3. Повторяемые объекты

Разобрать контейнер и внутренний cycledApplicantAnswers/профильный список по фактическому DTO. Не пытаться читать компонент ребёнка как единственный глобальный sN_cN. Сохранить порядок, количество, обязательные поля каждого элемента и выбранный способ документа.

Варианты проверять отдельно: вручную документ, профильный документ, иной источник документа, только актовая запись, документ личности при достижении соответствующего возраста. Конкретные коды вариантов и возраст берутся из текущих настроек/регламента, не из навыка.

Актовая запись и свидетельство — разные данные. «Кем выдан документ» нельзя автоматически использовать как «Орган актовой записи». В профильном компоненте имена полей иногда не соответствуют названию видимого документа; читать fields/storedValues и реальный DTO, не переименовывать предположительно неправильный ключ в VM.

## 4. Пустые и сложные необязательные поля

minOccurs=0 — элемент можно не создавать. Если создали, его тип, minLength/pattern и обязательные дети действуют. Для строки проверить существование/null и непустоту после trim; trim в условии не требует менять выводимый текст. Не применять строковую проверку к числу 0/boolean false.

Схематический паттерн ниже допустим только после подтверждения методов/псевдонима в движке:

```velocity
#if($s12_c1 && $s12_c1.toString().trim() != "")
<ns:OptionalText>$s12_c1</ns:OptionalText>
#end
```

Это не инструкция добавить toString/replace ко всем выводам. Для known String допустима её подтверждённая проверка trim. Для отсутствующего вложенного объекта сначала защитить родителя. Необязательный блок не создавать частично, когда внутри обязательны номер/дата/орган, и не подделывать эти данные ради схемы. Если нужный смысл можно передать в разрешённом дополнительном блоке, документировать XPath и основание такого mapping.

## 5. Файлы и подписи

По фактическому DTO FileUploadComponent может содержать uploads[], PhotoUploadComponent — один объект fileName/mnemonic/fileExt/mimeType. Не выполнять foreach по uploads у фотографии без такого поля. Каждый загрузчик имеет собственный uploadId и условие применимости. Проверять весь набор, не только первый файл.

Сформированный PDF заявления, пользовательское приложение и отсоединённая подпись — разные объекты. PDF включать в XML только с подтверждённым платформенным именем/mnemonic/MIME. Расширение не добавлять повторно к mnemonic, который его уже содержит. В пакете сверить ссылки и реальные объекты.

Выключение конкретного способа подписи заявления не требует удаления SIG к подтверждающему документу. Подпись нотариуса и подпись подающего имеют разные назначение/контракт. Форматы и размер одного файла/суммарного пакета не брать из чужой услуги. Не считать архив автоматически допустимым или недопустимым без матрицы загрузчик × документ × способ подписания.

## 6. Даты и экранирование

Даты документов календарные. Использовать подтверждённый dateTool/формат эталона, поддержать реальный ISO и dd.MM.yyyy. При ISO отдельно проверить сохранение первых 10 символов как дня, если обработчик часового пояса иначе сдвигает дату. Не заменять работавший dateTool самодельным макросом. Проверить крайние сутки и все даты документа, а не только рождение.

Не добавлять цепочки toString/replace/replaceAll без необходимости и проверки. Прямой вывод из действующего эталона не доказывает автоматическое экранирование. XML &, <, >, кавычки и переносы проверять реальным рендером; JSON-описание PDF имеет другие правила экранирования. Не экранировать дважды. Запрет символов во вводе не заменяет корректную сериализацию.

## 7. PDF-структура

PDF-VM может быть описанием компонентов JSON-массивом, а не HTML. Сохранять формат эталона. FormStep — самостоятельный верхний раздел; Panel — подраздел. Общий раздел повторяемых объектов с последовательными заголовками «Объект 1», «Объект 2» либо соответствующим термином услуги. Для детей — «Сведения о детях», «Ребёнок 1» и далее, если применимо. Номер брать от цикла/поддерживаемого механизма, не кодировать статически два элемента.

Соблюдать осмысленный порядок разделов по заявлению/регламенту; данные получателя/связанных взрослых и затем повторяемые объекты, когда так устроена форма заявления. Печать «Представитель» и основания представительства отделить от данных получателя. Нельзя печатать технический код отношения.

Проверки: число объектов/порядок/нумерация; отсутствие чужих разделов; все контакты и адреса; полный длинный текст; ссылки на файлы; отсутствие ${...}/$sN/#if в печати; перенос длинных значений и страницы. Успешный разбор PDF-текста не доказывает отсутствие наложений и обрезки.

## 8. Диалект и диагностика

Использовать [правила Velocity](velocity-rules.md). До подтверждения поддержки не применять #macro нигде и не добавлять вычислительный пролог перед корнем XML/массивом PDF. #set внутри корня также не считать автоматически разрешённым. Условия/циклы разворачивать напрямую. Локальный Apache Velocity — отдельная стадия, не доказательство штатной валидации.

При undefinedVariables сверить имя, активный экспорт, удалённые поля и загруженную в конструктор версию обоих шаблонов. При VAR_DUPLICATE_VIA_BLOCK_USAGE проверить конфликт локального имени с form-backend и вложенными блоками; не переименовывать поля storedValues вместе с локальной переменной. При HTTP 409 получить тело ошибки/UUID/path/версию, не приписывать причину макросу по коду HTTP.

При отсутствии XML проверить по очереди: текущий display и достижение подписания; настройки генерации вроде turnOffXmlGenerating; generatedFiles/fileGenerateActions; ответ валидатора; источники активной ветки; XSD и рендер. Снимок до подписания с пустым generatedFiles не доказывает сбой генерации. Оба шаблона сохранить и повторно проверить в штатном контуре; прежний успех другой редакции не переносить на новые байты.
