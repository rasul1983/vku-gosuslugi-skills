# Переходы, восстановление графа и кнопки

## 1. Инвентарь и состояние

Извлечь screens, applicationFields, screenRules, cycledScreenRules, init/initScreens, externalScreenIds, logicComponents, terminal и кнопки. Экран существует отдельно от компонента, а скрытый Redirect — компонент, выполняющий переход. Системный внешний экран не объявлять отсутствующим без проверки внешнего контракта. nextDisplay=null во вложенном сценарии может быть штатным завершением элемента.

Для каждого правила записать источник, цель, набор условий, значения, тип сравнения и visited, если он задан. Модель состояния должна знать только действительно пройденные ответы и подтверждённые особенности возврата. Непосещённый условный вопрос не равен «Нет»: часто он отсутствует. Не проверять маршрут по искусственному одновременно полному набору несовместимых ответов.

## 2. Проверка для каждого сценария

Для каждой цели × допустимой роли × существенных условий пройти граф от фактического init:

- на каждом автоматическом узле должен выбираться один следующий экран;
- ноль подходящих правил — пробел/неверный путь/value/visited;
- несколько — возможное пересечение; показать конкретное достижимое состояние, а не только формулу;
- цикл без изменения состояния/выхода — ошибка; конечный вложенный цикл — не ошибка;
- логический конец — отказ или штатная отправка, а не просто последний узел локального графа.

Число перечисленных статических маршрутов не равно числу браузерных прогонов. Статическая модель должна явно описать допущения: внешние компоненты, циклы, территория и подпись могут быть заменены абстрактным успехом. Эти допущения не объявлять протестированными.

## 3. Условия И/ИЛИ в конструкторе

В изученном редакторе одна карточка перехода объединяет условия только через И. Для `(A И B) ИЛИ C` создать две карточки между теми же экранами: первая A+B, вторая C. Не вставлять «ИЛИ» строкой в значение. Проверить, как платформа считает два сработавших правила к одному экрану: не полагаться на схлопывание, если это не подтверждено.

Для взаимоисключающей реализации можно использовать `A+B` и `НЕ(A И B)+C`, но отрицание должно раскладываться в реально поддерживаемые карточки/сравнения. Часто проще вычислить единый boolean в ValueCalculator и иметь true/false. Это способ снизить сложность, не обязательное переписывание простого работающего перехода.

Одного параметра достаточно, если он обеспечивает однозначность во всех достижимых состояниях. Не требовать добавления роли/цели/всех прошлых ответов в каждое правило. Безусловный переход рядом с условным подозрителен, но окончательный вывод зависит от семантики правил платформы.

Матрица для переноса: `откуда | куда | карточка № | компонент | тип | оператор | значение | И с другими условиями`. Альтернативные карточки писать отдельными строками. После выбора в UI проверить маркер выбранного экрана/компонента и повторно открыть сохранённое правило; закрытый список сам по себе не доказывает сохранение.

## 4. Возврат и смена ветки

Проверить реальные цепочки: ветка с дополнительным документом → назад → ветка без него; представитель → другой тип полномочий; поиск → ручной ввод → поиск; второй адрес → совпадение. Наблюдать очистку и финальные документы. Техническое clearCacheForComponentIds может не быть доступно в UI; не давать невыполнимую инструкцию.

Условие исправлять минимально после подтверждения сохранённого ответа и его влияния. Отдельная защита VM — выбирать активную ветку по управляющему ответу независимо от наличия старых данных. Работающая очистка одного квиза не гарантирует очистку всех виджетов.

## 5. Кнопка по следующему видимому действию

Для каждого текущего экрана вычислить nextVisible: пройти только прозрачные автоматические узлы с текущими данными до следующего пользовательского действия. Не считать скрытый Redirect отдельным шагом, но не пропускать загрузчик, карту, подтверждение профиля и вопрос. Если до подписания есть ещё действие — «Продолжить»; если следующий шаг — подписание, применять подпись по действующему стандарту. В изученном чек-листе есть исключение: при единственном способе простой электронной подписи предыдущая кнопка может называться «Продолжить». Не удалять это исключение из методики.

Если одному экрану соответствуют разные nextVisible, использовать взаимоисключающие подписи. Не перемещать экраны ради текста кнопки. MapService может иметь встроенную «Выбрать» и сразу переходить в MiniApp — это проверяется по реальному UI, а не добавлением второй кнопки.

## 6. Полная схема ValueCalculator → кнопки

Синтетический пример: s10_c2 — вычислитель, s11_c1 — ответ «Да» о дополнительных документах. IDs заменяются после инвентаря; это не бизнес-правило услуги.

В Вычисляемые аргументы (linkedValues) вычислителя:

```json
[
  {
    "version": 1,
    "argument": "buttonMode",
    "jsonLogic": {
      "if": [
        {"==": ["answer.s11_c1.value", "Да"]},
        "CONTINUE",
        "SIGN"
      ]
    }
  }
]
```

Если ответ обязателен и отсутствие означает ошибку, добавить отдельный режим/защиту; пример предполагает, что ответ уже получен. Вычислитель должен быть включён в logicComponents исполняемого до кнопки экрана и пересчитываться после возврата. Его type=ValueCalculator — тип компонента; relatedRel содержит фактический ID, который может отличаться от слова ValueCalculator.

Кнопки соответствующего экрана:

```json
[
  {
    "label": "Продолжить",
    "type": "nextStep",
    "action": "getNextScreen",
    "attrs": {"ref": [{"relatedRel": "s10_c2", "path": "arguments.buttonMode", "relation": "displayOn", "val": "CONTINUE"}]}
  },
  {
    "label": "Перейти к подписанию",
    "type": "nextStep",
    "action": "getNextScreen",
    "attrs": {"ref": [{"relatedRel": "s10_c2", "path": "arguments.buttonMode", "relation": "displayOn", "val": "SIGN"}]}
  }
]
```

screenId оставить пустым/не задавать по формату конструктора; screenRules продолжают определять маршрут. В UI зависимости: «ID атрибута» = s10_c2, «Путь» = arguments.buttonMode, тип «Строка», значение SIGN/CONTINUE, действие displayOn. «Идентификатор кнопки» — собственный ID кнопки, не вычислитель.

## 7. Контроль после экспорта

Существует ID вычислителя; linkedValues — массив; имя argument точно совпадает с path, включая суффиксы; logicComponents включает его; входы доступны до вычисления; обе кнопки nextStep/getNextScreen; прямых целей нет; ровно одна подходящая кнопка; required не обходится; фактический nextVisible соответствует тексту. Для каждой подписи проверить случай «последняя загрузка», «есть ещё документ», «есть карта», «вопрос не посещён» и возврат.
